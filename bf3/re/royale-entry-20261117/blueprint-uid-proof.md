# GameObjectData.indexInBlueprint и диагностический UID assertion

17.11.2026. Только статическое чтение локальных PE. Новых патчей кода или памяти для UID не внесено.

## Вывод

В release-client BF3 существует прямой эквивалент обоих server UID builders. Он **без проверки** включает `GameObjectData.indexInBlueprint == FFFF` в обычный поток вычисления UID. Debug dedicated-server при том же значении сначала выводит assertion, а затем продолжает тот же алгоритм. Поэтому сама строка `Trying to get uid for object not created from blueprint` не доказывает остановку загрузки или необходимость исправлять конструктор. Если сервер после неё продолжает кадры, её надо классифицировать как диагностику, а причину последующей неисправности искать по фактическому поведению.

`liveEditingEnable=1` не является способом автоматически назначить UID: ветка для FFFF возвращает **нулевой UID**, обходя обычный алгоритм. Включать её ради удаления сообщения было бы изменением поведения.

## Сопоставленные функции

| Назначение | Release zbf3.exe | Debug dedicated server |
|---|---|---|
| UID builder, обычная цепочка | 00548A20 | 005CD4D0 |
| UID builder с готовым родительским ID | 00548B00 | 005CD680 |
| Запись байтов в поток | 0042A8C0 | 00444630 |
| Начальное нулевое UID value | 01EF39F0 | 022B0A40 |

Release 00548A45 получает data; 00548A4C читает `mov dx,word ptr [ecx+8]`. Инструкции 00548A50–00548A68 переставляют байты и записывают ровно 2 байта. Никакого сравнения с FFFF, дополнительного индекса или раннего возврата здесь нет. Затем 00548A6D–00548AAB обходят parent+08 chain, вызывают vtable+3C у каждой записи и добавляют следующие 2 байта. В конце поток финализируется и его результат записывается в выходной UID.

Release 00548B26–00548B49 так же безусловно записывает data+08. Его parent branch 00548B60–00548BC4 совпадает по условиям с server005CD7C0–005CD824: чтение parent+14, маска 1FFFFFFF, запись готового 4-byte ID через bswap либо продолжение цепочки двухбайтовых parent index.

Server005CD4F5 проверяет global byte02AF7ED3 (`liveEditingEnable`), затем005CD503 читает word[data+8]. При выключенном live editing и FFFF сообщение формируется в005CD539–005CD5B4.004AB220 управляет только возможным breakpoint:005CD5C0 пропускает `INT3` в005CD5C2 при false. После него005CD5C3 восстанавливает исходный индекс и005CD5C7 начинает тот же byte-swap/write sequence, что release. Вторая функция аналогична: условный breakpoint005CD789; восстановление005CD78A, запись005CD78E–005CD7A7.

## Почему live editing не генератор

При liveEditingEnable и FFFF server005CD51B вызывает005E4A20. Тело этой функции: `mov eax,02B1BF3C; ret`. Затем вызывающий просто копирует DWORD по этому адресу. Объект02B1BF3C инициализируется статическим initializer02264140 →022B0A40. Последний — `mov eax,ecx; mov dword ptr [eax],0; ret`. Иными словами, результат этого обхода — общий нулевой UID, а не уникальная последовательность и не новый indexInBlueprint.

## Проверка конструктора VU

VEXT `ReferenceObjectData()` входит в14668460. В146684B7 ищет TypeInfo по настоящей строке ReferenceObjectData; из TypeInfo.info получает factory+14. В146684D2–146684D7 вызывает factory с `(memory=0, arena=[18E74CF0], thirdArgument=0)`. Далее146684E5→10F02660→10F2EDA0→107CAF90 оборачивает указатель и управляет native reference/ownership. В этой цепочке нет автоматической записи в native data+08. Опциональная ветка107CB069 включается параметром `-tracedc` (строка собирается в107035D3): singleton10D5FF80, vtable178579BC+00→10D607F0 только считает обращения к указателю во внутренней map+64, сам GameObjectData не меняет. Сам setter GameObjectData.indexInBlueprint присутствует отдельно:12CDD860, фактическая запись word[data+08] после проверки writable.

В vu-core.dll.ev-orig нет абсолютных ссылок или относительных call на00548A20/00548B00; в исследованных местах не найден hook, меняющий этот UID flow. Это статическое свидетельство для данных бинарников, а не утверждение обо всех версиях VU.

## Практическое решение для текущей сборки

Не менять мод, не включать liveEditingEnable и не назначать придуманные индексы из общего DataContainer factory. Оставить настоящий диагностический вывод. Проверять, прошла ли загрузка/создание spawn после него; если да, строка не является текущим startup blocker. Отдельно одинаковые index + одинаковая parent chain могут дать одинаковые UID; наличие конкретной коллизии здесь не проверялось и из одной строки assertion не следует.

Дизассемблирование воспроизводится `team_capacity_probe.py client 00548A20 430`, `server 005CD4D0 180`, `server 005CD580 80`, `server 005CD680 115`, `server 005CD7AC 190`, `server 005E4A20 32`, `server 02264140 16`, `server 022B0A40 16`, `vext 14668460 170`.

SHA-256 client/VEXT/core записаны в соседнем visual-environment-report.md. Для UID изучен именно выделенный `D:/Games-cache/royale/server-runtime-v3/bf3_server_Final.exe` (SHA-256 `F39F7623063CFDE9C449A0BDC9A57448D2D137D6DEF00B17EA04800EDA955470`), а не клиентский exe с другим набором адресов.
