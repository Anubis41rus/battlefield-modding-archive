# Server selector 01175A60: расширение временного массива до team127

17.11.2026. Исследование ограничено функцией01175A60–01175D92. Игры не запускались. Все исполняемые проверки выполнялись в отдельном fixture-процессе, на собственных копиях кода и собственных данных.

## Контракт функции

`int __cdecl SelectTeam(settings*, bool overrideSelection, int previousTeam)`; аргументы подтверждены всеми четырьмя call sites:011904BD,011905FD,01191497,01191644. Все caller снимают12 байт после вызова. Настройки режима читаются из settings+64. Соответствующий enum в локальных VU-Docs: TeamAssignMode, TamEqualTeams=0, TamFullTeams=1, TamOneTeam=2.

Менеджер игроков: `[global02B3EE2C]+30`; helper подсчёта игроков — **00E5F110**, thiscall(manager,team). Источник количества team slots — `(DWORD[0285BB3C]-DWORD[0285BB38])/8`. Slot0 нейтральный; циклы перебирают1..slotCount-1. PreviousTeam уменьшает эффективное количество на1. Mode2 при выключенном override сразу возвращает1; mode0/override выбирает минимально заполненную допустимую команду. Mode1 сохраняет особые native ветви полного заполнения/двух активных команд. Неизвестный mode возвращает0 через существующий диагностический путь.

## Реальный выход за стек

Оригинал резервирует0x178 байт плюс четыре сохранённых регистра. В mode1:

- 01175AA5 задаёт memset длиной0x44, base массива после возврата — `ESP+14`.
- 01175B1D пишет `int counts[team]` по `[esp+esi*4+14]`.
- 01175B50 читает по `[esp+ecx*4+14]`.

Цикл записи ограничен динамическим TeamSize vector, а не17. Поэтому расширение только global vector до128 опасно: запись counts[127] выходит из старого frame. Это реальный memory-safety blocker, в отличие от сообщения UID, разобранного отдельно.

## Исправление: семь инструкций того же размера

Увеличить резерв stack frame на0x1C0:0x178→0x338. Изменить обращения к аргументам на тот же сдвиг и оба выхода. Все семь инструкций сохраняют длину, branch/call relocation не требуется.

`memset44` остаётся. Это намеренно и безопасно: единственный путь к indexed read01175B50 проходит через завершённый цикл01175B10–01175B39, который уже записал **каждый** counts[1..slotCount-1]. Slot0 не читается. При128 slots все потенциально читаемые128-entry-array значения определены до чтения.

Старый diagnostic object на `ESP+58` используется только в ветке неизвестного mode01175C9C–01175CD3. Эта ветка не использует counts: для mode1 управление туда не попадает. Поэтому его адрес не надо переносить: массив и diagnostic scratch имеют непересекающиеся времена жизни. Остальные assert-пути в mode1 передают статические аргументы, а не этот объект. Fixture отдельно прошёл диагностическую ветку с записью полного0x120-byte scratch buffer.

После патча counts занимают `[ESP+14,ESP+214)`, а return address находится на `ESP+348` после сохранения регистров. Сдвиг0x1C0 кратен16: исходное выравнивание стека сохраняется. Максимальная резервация меньше страницы; дополнительный stack probe не требуется.

Все семь мест должны проверяться и применяться **в одной транзакции с переносом TeamSize vector**. Частичное расширение vector или частичное изменение offsets не разрешено. Сигнатуры и общий env-off ведёт NativeTeamCapacity/агент royale_team_limit; здесь существующие production-файлы не менялись.
