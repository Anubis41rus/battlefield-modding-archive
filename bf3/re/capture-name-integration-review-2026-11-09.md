# Статическая сверка интеграции CP.name — 09.11.2026, подготовка 264

Прочитаны только уже сохранённые `re/mode-*.txt`, VU `FUN_10E06C60` в удержанной декомпиляции и текущие исходники. Бинарники не открывались. Тесты, harness, игра, сервер, установки, doctor и сборка не запускались. Код не менялся. Это проверка параметров для интеграции родительским агентом, не подтверждение поведения в игре.

## ABI

Для x86 thiscall ниже допустим адаптер `__fastcall(self, unusedEdx, ...stackArgs)`: второй регистровый аргумент не должен сдвигать стековые параметры.

| VA | Вызов | Результат и очистка стека |
| --- | --- | --- |
| `00440B90` | thiscall, `ECX=arena`, аргументов на стеке нет | `EAX=arena`, `ret`; конструктор scratch allocator scope |
| `00E49200` | thiscall, `ECX=list`, один stack arg `&arenaPtr` | `EAX=list`, `ret 4`; передавать адрес переменной с указателем arena, не сам arena как единственный аргумент |
| `005E1260` | cdecl, шесть stack args: `arenaPtr, &key8, SpawnRefTI, &busContext, bus, list` | вызывающий снимает `0x18`; возвращаемое значение вызывающим CP не используется |
| `005CD2D0` | thiscall, `ECX=node+8`, один stack arg `1` | `EAX=Entity*` либо 0, `ret 4`; это значение соответствует VU name getter, native CP для собственных операций использует 0 |
| `00E44F00` | thiscall, `ECX=CharacterSpawnEntity*`, без stack args | `EAX=const char**` — адрес fb::String, один dereference даёт CString; `ret` |
| `00E44030` | thiscall, `ECX=list`, без stack args | clear списка, `ret`; сам sentinel не переустанавливает |
| `0043F510` | thiscall, `ECX=arena`, без stack args | уничтожает allocator scope и восстанавливает предыдущий static TLS context; `ret` |

`key8={dataPtr=[cp+0x14], fieldId=0xECEA613A}`. `SpawnRefTI=0x02C02D9C` — нативный аргумент запроса `SpawnReferenceObjectData`. Фильтр результата перед чтением имени: `ServerCharacterSpawnEntity`, TypeInfo `0x02C16B84`. Команда не является аргументом getter/запроса.

`00E44F00` разрешает **runtime property override** через bus/context и `02351500`, hash `0x58D1C621`, data offset `0x120`. Чтение только `[data+0x120]` этому не равно. Имя надо скопировать в собственный ограниченный буфер до cleanup и до передачи Lua; возвращаемый адрес не предназначен для хранения между тиками/сменами уровня.

## Размеры и структура

- Arena: `0x18` байт. Поля ctor: vtable+0, ref/state+4/+8, allocator+0xC, прежний TLS scope+0x10, packed tag+0x14.
- Fixed list: `0xA48` байт. Подтверждено нативным размещением list=`esp+0x1AC`, следующего arena=`esp+0xBF4`. Sentinel next/prev — первые два DWORD; конец обхода — сам адрес list.
- Node: `0x28` байт; next=`[node]`, объект результата для `005CD2D0` начинается в `node+8`.
- Bus context: в native CP передаётся 8-байтовый буфер, заполняемый `bus.vtable+0x30`, thiscall(bus, contextOut). Выделение 16 обнулённых байт с запасом не меняет первых 8; доказанный контракт — 8. `key8` и `busContext8` — разные объекты.
- Выравнивание всех указателей/буферов как минимум 4; запасное alignas(16) не противоречит сохранённым вызовам.

## TLS: два независимых механизма

Allocator ctor `00440B90` и dtor `0043F510` используют **static PE TLS**:

```text
FS:[0x2C] -> vector
index = DWORD[absolute 0x02B6AA74]
block = vector[index]
scope = DWORD[block+0x118]
```

Ctor сохраняет прежний scope в `arena+0x10` и последним действием ставит `[block+0x118]=arena+0xC`. Dtor освобождает scope-ресурсы через `0043E3F0`, затем восстанавливает `[block+0x118]` из `arena+0x10`.

Существующий `OnEngineThreadCtx` в `VextPlayerManager.cpp` читает **другой**, dynamic Win32 TLS index из `base+0x027BCCD4` и вызывает `TlsGetValue`. При base=400000 это absolute `02BBCCD4`, а не `02B6AA74`. Эта проверка не подтверждает наличие static TLS block; её true/false нельзя переносить на allocator TLS.

Перед arena необходима отдельная проверка читаемости static TLS vector/index/block и доступа к `block+0x118`. Нулевой предыдущий scope сам по себе допустим: ctor его сохраняет, dtor восстанавливает. Вызов и cleanup должны оставаться в одном потоке. Материалы не доказывают безопасность обращения к bus/EntityWorld из любого произвольного потока лишь по наличию static TLS; надо сохранить принятый в интеграции engine-thread/lifetime guard.

## Cleanup и исключения

Нативный порядок `01337C64–01337C9A`:

1. `Clear(list)` через `00E44030`.
2. Установить `list.next=list.prev=&list`.
3. `DestroyArena(arena)` через `0043F510`.
4. `Clear(list)` повторно — уже пустой список.

Не пропускать шаг 2: Clear освобождает/возвращает элементы, но оставляет прежние ссылки sentinel; второй Clear иначе снова пойдёт по бывшим nodes после уничтожения arena.

Нужно раздельно учитывать завершение ctor arena и ctor list. При исключении до завершения ctor list нельзя считать, что Clear пригоден: ctor сначала обнуляет head, а self-ссылки ставит только в конце (`00E4927A/7C`). При исключении в первом Clear всё равно требуется попытка восстановления TLS arena; один общий `__try` вокруг всех cleanup-вызовов может пропустить dtor. Если native dtor сам не завершился, сохранённый заранее static TLS scope позволяет не оставить в TLS указатель на уходящий стековый arena; это аварийное восстановление указателя, не доказательство полного освобождения ресурсов. Поведение частично сконструированных/повреждённых контейнеров материалами не проверено.

## Пустая строка VU и раннее отсутствие имени

VU `FUN_10E06C60` возвращает пустую std::string, когда CP не разрешён, список не содержит подходящего связанного CharacterSpawn или у всех подходящих результатов getter возвращает null. Null getter отдельного результата продолжает обход. Как только связанный CharacterSpawn дал ненулевой адрес fb::String, VU копирует CString и заканчивает поиск **даже если строка пустая**. Поиск следующего непустого имени отличался бы от этой реализации. Успех чтения и длина строки — разные признаки.

Это не делает временный отказ нового слоя (нет нужного TLS, уровень выгружается, native snapshot ещё не получен) авторитетным успешным empty. Нужен отдельный pending/error/success статус.

В прочитанном текущем Lua `cpEntity` кэширует синтетическое имя `EVBOTS_CP#[_HQ]`; `refreshCp` обновляет состояние. В fun-bots `_InitFlagTeams` относит базу по суффиксу `HQ`; `_TranslateObjective` сохраняет сопоставления в `m_Translations[name]` и позиции в `m_ObjectivePositions[name]`. Поэтому замена всех ранних отказов на `name=''`:

- превращает HQ в обычный флаг при начальной классификации;
- делает одинаковым ключ `''` разных CP;
- может закрепить временный результат в кэше раньше готового native снимка.

Интеграция должна отличать неподготовленный снимок от успешно полученной строки и не закреплять pending как истинное имя. Если используется временный стабильный ключ, смена на настоящее имя должна учитывать уже запомненные ключи мода; если отложенное создание CP-обёртки — готовность объектов/LevelLoaded не должна опережать получение их снимков. Как именно это реализовать — решение родительского агента. Подтверждать отсутствие игровой регрессии без разрешённых пользователем проверок нельзя.

## Итог

ABI/размеры/возвращаемый указатель и нормальный cleanup подтверждаются сохранёнными материалами. Существенные риски интеграции: подмена static TLS guard динамическим, неправильный уровень указателя в аргументе ctor list, пропуск sentinel-reset/arena cleanup при ошибке и смешивание pending имени с успешной пустой строкой. Новый бинарник/готовая 264 в рамках этого отчёта не проверялись.
