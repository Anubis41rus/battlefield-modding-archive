## Что доказано

1. `ServerLifeCounterEntity::onEvent`, VA `0x012DC140`, сравнивает:
   - `0x2CFC2C6C` (754723948) → `0x012DC317` → `0x012D9380(1)`. Эта функция увеличивает `[self+0xAC]`, проверяет порог и пополняет жизни; не конструирует сообщение BaseDestroyed. В EBX имя входа — `IncreaseReinforce`.
   - `0x324B3FE6` (843792358) → `0x012DC212`. При прежнем `[self+0xBC]>0` уменьшает этот счётчик и конструирует точное сообщение `ServerGameplayPlayerBaseDestroyedMessage`. В EBX имя — `DestructBase`.
2. Конструктор `0x023C7F00`: категория сообщения `0x50A2F3EA` (`ServerGameplay`), тип `0x0E585CA4`. Код `0x012DC239–0x012DC27A` заполняет `msg+0x28` игроком, `msg+0x2C` признаком последней базы, `msg+0x30` самим счётчиком. Последняя база: счётчик после уменьшения `<=0` и `[data+0x98]==0` (не атакующий).
3. В штатном prefab Rush атакующий счётчик GUID `7435DBA1-E2ED-421A-811E-6541803493E0` имеет `Attacker=True`, `BaseCount=0` и принимает `IncreaseReinforce`; защитный GUID `8326CBCE-7228-4BC4-8DE5-8B3768AE33E4` имеет `Attacker=False`, `BaseCount=5` и принимает `DestructBase`. Поэтому эта проводка даёт один сигнал BaseDestroyed от защитного счётчика; одинаковое продвижение по обоим входам — ошибка моста. Другие пользовательские prefab этим не проверены.
4. `rushEvent` сейчас продвигает стадию по обоим входам, передаёт `final=false` всегда и склеивает события временным фильтром `os.clock()>3 с`. Это не семантика движка: `IncreaseReinforce` не должен продвигать стадию, законный быстрый следующий `DestructBase` не должен теряться, а отключённый/исчерпанный счётчик не должен давать ложный сигнал лишь по факту получения входа.
5. `l_em_ev_unwatch_all` обнуляет только список наблюдаемых сущностей. `g_evRead` не догоняет `g_evWrite`, следовательно, кольцо сохраняет входы прошлого уровня. После повторного использования адреса они могут быть сопоставлены с новыми `kindOf`/callback. Это статически подтверждённая возможность; факт такого попадания в прогоне друга неизвестен.

## Можно ли взять точное сообщение через уже имеющийся RCON-хук

В полном теле `RconServer::onMessage`, `0x01152A00–0x011532C9`, нет ветки ни по категории `0x50A2F3EA`, ни по типу `0x0E585CA4`. Обработчик обслуживает другие категории/типы. Его подписка на ServerGameplay не установлена. Поэтому добавление проверки BaseDestroyed в наш RCON-detour не даёт доказанного источника: получение сообщения этим экземпляром неизвестно.

Новый перехват общего диспетчера ради этого не предлагается. Ближайшее уже перехваченное место — существующий `EvDetour`, оборачивающий именно `onEvent` счётчика.

## Минимальное исправление без нового native patch — рекомендация

Точные guard из `0x012DC140` (capstone по выбранному exe):

```text
012DC14C call 0x008493D0              ; базовый onEvent выполняется первым
012DC151 test byte ptr [esi+0x0A], 1
012DC155 je   0x012DC320             ; бит выключен — вход отвергнут
012DC15B cmp  byte ptr [esi+0xC8], 0
012DC162 jne  0x012DC320
012DC168 cmp  byte ptr [esi+0xC9], 0
012DC16F jne  0x012DC320
012DC175 mov  eax, [edi+4]           ; id входного EntityEvent
012DC207 cmp  eax, 0x324B3FE6         ; DestructBase
012DC212 mov  eax, [esi+0xBC]         ; baseAliveCount до уменьшения
012DC218 test eax, eax
012DC21A jle  0x012DC293             ; если <=0 — сообщение не конструируется
012DC21C dec  eax
012DC225 mov  [esi+0xBC], eax
012DC250 cmp  dword ptr [esi+0xBC], 0
012DC25B jg   0x012DC26D             ; больше нуля — final=false
012DC25D mov  ecx, [esi+0x14]        ; ссылка на LifeCounterEntityData
012DC260 cmp  byte ptr [ecx+0x98], 0 ; attacker
012DC267 jne  0x012DC26D             ; атакующий — final=false
012DC269 mov  al, 1                 ; иначе final=true
```

Снимок до оригинала воспроизводит перечисленные guard, но строгое подтверждение принятого входа требует сравнения `BC` до и после оригинала: базовый `onEvent` вызывается до проверок, а не после. Рекомендация — сохранить `before`, вызвать оригинал, затем публиковать `accepted=(before>0 && after==before-1)` и сохранённый final. Один только снимок до оригинала подтверждает готовность входа, но ещё не выполнение уменьшения. Тип надо ограничить доказанным `ServerLifeCounterEntity`/его обработчиком: читать эти поля у произвольной Entity нельзя.

- `IncreaseReinforce` оставить обычным входом Entity callback, исключив продвижение стадии.
- Для проверенного оригинала `onEvent=0x012DC140` и входа `DestructBase` сохранить `BC` до оригинала и после; отдавать отдельные метаданные разрушения в существующее кольцо только при реальном уменьшении положительного `BC`. Это использует уже поставленный хук и не считает непринятый вход событием.
- Сохранить `final` в момент события; не читать его позже, когда пакет уже мог содержать несколько событий. `final=(BCafter==0 && !attacker)` по подтверждённому коду.
- Продвигать стадию по принятому разрушению без трёхсекундного фильтра. Для штатной проводки один защитный счётчик уже обеспечивает один сигнал на сектор. Если нужна дедупликация нестандартного prefab, использовать идентичность счётчика и состояние, не время.
- При `UnwatchAll` отменять очередь прошлого уровня (`g_evRead` догоняет опубликованный `g_evWrite`), при Lua LevelReset сбрасывать накопители опроса/списки спавна, чтобы не удерживать адреса до окончания TTL.
- Проверки: пополнение не меняет стадию; `DestructBase` у исчерпанного/отключённого счётчика не меняет её; два настоящих разрушения с интервалом менее 3 с оба доходят; последняя база передаёт true; событие старого уровня не доставляется после сброса.
