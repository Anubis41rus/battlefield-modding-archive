# Поля ServerPlayer из диффа «ранний / поздний / человек»: что они значат

> 15.10.2026, только чтение. Разбирал `bf3_server_Final.exe` (база 0x400000) статически: capstone и поиск записей.
> Дифф: A — ранний бот `BOT_Lumenko125`, B — поздний бот `BOT_Ethan`, C — человек.

## 1. Что значат поля из диффа

| Поле | Что это (по коду) | Основание | Связано с иконкой или ником? |
|---|---|---|---|
| `+0x094..+0x317` | Встроенное множество анлоков и перков игрока (красно-чёрное дерево со своим пулом узлов) | Конструктор Player `0x008CCCA0` → `lea ecx,[esi+0x94]; call 0x008CA6A0`. Там: `+0x98` — узел-заголовок (сам на себя), `+0xA4` — **количество**, `+0xA8..+0xB4` — пул (свободный список, начало, конец, размер узла 0x10; `0x00565690`), с `+0xB8` — встроенный буфер 0x25F байт (`push 0x25f` в `0x008CA703`) | **Нет.** `+0x260..+0x2CC`, `+0x2D4`, `+0x2E0`, `+0x308` лежат внутри буфера `+0xB8..+0x317`: это узлы дерева (левый, правый, родитель с цветом, значение = указатель на UnlockAsset). Разные «гнёзда» самоуказателей у A и B (`+0xB8/+0xD8…` и `+0xA8/+0xC8…`) — те же узлы и заголовок. Узлы лежат по-разному, потому что множество очищали и наполняли в разном порядке (`0x00E2C1D0` очистка, `0x00E299A0` вставка). Смысловое поле здесь одно — `+0xA4` (количество): A=26, B=25, C=4. У ботов наборы почти одинаковые |
| `+0x36C` | Поле `+0x4C` сетевого подобъекта игрока `+0x320` (vtable `0x025C7764`, конструктор `0x01A35C00` обнуляет `+0x4C`) | конструктор ServerPlayer `0x00E350B0`: `lea ecx,[esi+0x320]; call 0x1a35c00` | Похоже на сетевой номер или счётчик. A=0x9A, B=0x9D, человек 0x7F — номера идут по порядку (гипотеза) |
| `+0x374..+0x380` | Сетевой хэндл: `+0x37C` — указатель на сетевой объект, `+0x380` — два 16-битных id | `0x01A35BA0` (тот, что ставит флаги `0x20/0x40`): `if ([this+8]==0) return;` при this=`игрок+0x374`, то есть **флаг ставится, только если `[игрок+0x37C] != 0`**; id берётся из `[игрок+0x380]` | Возможно: запись кита или перков ДО появления сетевого объекта не помечается «грязной». В диффе этих полей нет — проверить вживую (§4) |
| `+0x3B8` | id игрока (A=0x0D, B=0x0E) | пишется в конструкторе `0x00E35160`; VU отдаёт его как `Player.id` (`0x10B995DD`) | нет |
| `+0x4B0` / `+0x4B4` | **Данные последней смерти**: `+0x4B0` — причина или категория (результат `0x00DD1E20`), `+0x4B4` — время (`0x0083D7C0`) | обработчик убийства `0x0117C720` (строка «RoadKill»): `0x0117C792 mov [edi+0x4B0],eax`, `0x0117C7AD mov [edi+0x4B4],eax`; обнуляются в конструкторе (`0x00E352C6/CC`) и в `releaseLevelDependencies` (`0x00E370A1`) | **Нет.** B=0 — поздний бот ещё не умирал |
| `+0x50C..+0x51C` (вектор), встроенный буфер с `+0x520` | Слоты оружия (кастомизация по слотам) | конструктор `0x00E3530B..0x00E3531C` | Блок `00000048, 02845120, ptr…` на `+0x56C` у A и C и на `+0x5B4` у B — это элементы вектора: у A заполнен слот, который начинается с `+0x568`, у B — слот с `+0x5B0`. Это разница в выборе оружия, не в иконке |

**Вывод (факт):** ни одно поле из диффа не управляет иконкой специализации или ником. Это раскладка пула перков,
сетевой счётчик, id, данные последней смерти и раскладка слотов оружия.

## 2. Откуда разница «ранний / поздний» в нашем коде (факт)

Сравнил `NativeCreateOne` (~2320–2700) и `LateCreateEngineImpl` + `InitLateBotFields` (~2760–2900) в `VextPlayerManager.cpp`.
Нашлось **одно** различие в вызовах движка:

- Ранний путь вызывает `addToTeam` (RVA `0x00D8EF80` = **VA `0x0118EF80`**, `VextPlayerManager.cpp` ~2726–2745)
  как `cdecl(игрок, команда, a3, менеджерОтрядов)`. Поздний путь `addToTeam` **не вызывает**.
- Настоящая сигнатура `0x0118EF80` по дизассемблеру: `cdecl(игрок=[esp+4], команда=[esp+8], bool=[esp+0xC], bool=[esp+0x10])`.
  Это видно по разбору стека: `sub esp,0x138; push ebx/esi/edi`, затем `edi=[esp+0x148]` (арг. 1), `esi=[esp+0x148]` после
  второго push (арг. 2), `bl=[esp+0x14C]` (арг. 4), `[esp+0x150]` (арг. 3, байт). Функция пишет в лог `addToTeam(`,
  «Attempted to add to full team», «Could not add to squad». **Четвёртым аргументом мы передаём указатель менеджера
  отрядов, а движок читает его младший байт как bool.** Это ошибка в сигнатуре нашего вызова (факт), её последствия не проверены (гипотеза).
- Штатно движок вызывает `addToTeam` из `balanceTeams` (`0x01190260`, «needSquadValidation / needTeamValidation»),
  из входа по токену Blaze (`0x01191920` «joinSquad(» ← `0x01329CE0` ← `0x01332D2E`) и из обработчиков приглашений и ESports
  (`0x01190D67/0x01190EB3/0x01190FEB`). Позднего бота команда, видимо, получает одним из этих штатных путей (`balanceTeams`
  или смена команды модом) с проверкой отряда (гипотеза).

Время создания:
- раннего бота создают из очереди до первого спавна человека, до того как его клиент «в уровне»;
- поздний бот создаётся, когда клиент человека уже в уровне.

Наблюдение координатора (первая иконка и ник есть ровно у тех, кто создан после первого спавна человека, и это не меняется
после респауна) указывает на данные, которые клиент получает **один раз при создании игрока или его сетевого объекта**.
Запись перков `0x01A35BA0(0x20)` и кита `(0x40)` — пустая операция, пока `[игрок+0x37C] == 0` (факт по коду).
Если сетевой объект ранних ботов появляется позже наших записей, флаги теряются, и клиент может не получить данные (гипотеза).

## 3. «Газ = 0» у позднего бота

Движок с этим полем не связан: ходьба в нашем мосту управляется своим объектом ввода `+0x3C0`, флагом `+0x318`,
`+0x3E8 == солдат`, `солдат+0x249` и физикой CPE (Lua ~847–852, `l_bridge_bot_own_input` ~4776).
`prePhysicsUpdate` (`0x00E34280`) читает ввод из `+0x3C0`. «Газ=0» значит, что в объекте ввода ноль, то есть уровни мода
до него не доходят. Отличающее поле статически не нашлось. Проверить вживую у A и B: `+0x3C0` (наш буфер из `MakeOwnInput`?),
`+0x318`, `+0x3E8`, `+0x31C`, а в Lua — `p.ownInputOn`, `p.input._native` позднего бота. У позднего `_native` ставится
в `CreatePlayer` (стр. ~770). У раннего — при привязке через метатаблицу (~107–118).
Ещё возможная причина (гипотеза): поздний бот не зарегистрирован в команде или отряде через `addToTeam`
(см. §2), и мод не даёт ему путь или цель. Это проверяется по логу мода, а не по движку.

## 4. Рецепт (сначала проверка, потом правка)

**Шаг 0 — пассивный дифф (только чтение), без него не править.** Тот же `peekdiff.py`, A/B/C, размер **0x800**
(нужно дотянуть до extent'ов) плюс точечно:
- `+0x378/+0x37C/+0x380` — сетевой хэндл. Если у A `+0x37C` появился позже записи перков или кита, причина в потерянных флагах;
- `+0x49C/+0x49D/+0x49E/+0x4A0` — флаги «в уровне» (см. SEQUENCE-REPORT §4);
- `+0x20/+0x24` (onlineId), `+0x318/+0x319`, `+0x3BC`, `+0x3C0`, `+0x3E8`;
- extent'ы: `VeniceServerPlayerExtent` по `игрок + [0x0285BAD8]`, размер 0x118 (узел регистрации `0x0285BAD8`:
  размер 0x118, align 8, typeinfo `0x02650DF0`, ctor `0x01181BD0`, vtable `0x02652BF4`);
  `VeniceServerPlayerPersistenceExtent` по `игрок + [0x0285BAA0]`, размер 0xC (`+4` byte, `+8` float; ctor `0x01175020`, vtable `0x02651014`).
  Смещения — значения глобалов `[0x0285BAD8]`/`[0x0285BAA0]` в живом процессе.

**Шаг 1 (дёшево, по факту из наблюдений).** Создавать движковых игроков из очереди ранних ботов только **после первого
спавна человека** и тем же путём, что поздних (`LateCreateEngineImpl`). Именно такие боты сейчас получают иконку и ник.
До этого держать их в Lua без движкового игрока, как делает очередь. Отдельно лечить «газ=0» позднего пути (§3).

**Шаг 2 (если шаг 0 покажет потерю флагов).** После того как у бота появился `[игрок+0x37C] != 0`, повторно вызвать штатный
обработчик выбора `0x00E331B0` с сообщением выбора (SEQUENCE-REPORT §5 п.2). Он сам поставит флаги `0x40/0x20` на `+0x374`.
Либо хотя бы повторить `0x01A35BA0(0x40)` и `0x01A35BA0(0x20)` на `игрок+0x374`. Это только вызовы штатных функций, байты не патчатся.

**Шаг 3 (исправление сигнатуры, факт).** Вызов `addToTeam` `0x0118EF80` в `NativeCreateOne` приведён к реальной сигнатуре
`cdecl(игрок, команда, bool, bool)`. Значения bool взять из живого вызова движка для человека (перехватчик уже снимает
аргументы). Как вариант для опыта — не вызывать его вовсе, как поздний путь.

Правило 18: всё перечисленное — вызовы штатных функций, а не патчи байт. Перед вызовом каждой функции сверить её пролог
по файлу exe (адреса выше получены дизассемблером и сверены по ходу функций).

`0x008CCCA0` ctor Player · `0x008CA6A0` init множества перков (+0x94) · `0x00E350B0` ctor ServerPlayer · `0x01A35C00` ctor сетевого подобъекта (+0x320) ·
`0x01A35BA0` флаг репликации (no-op при `[+0x37C]==0`) · `0x0117C720` обработчик убийства (+0x4B0/+0x4B4) ·
`0x0118EF80` addToTeam `cdecl(p, team, bool, bool)` · `0x01190260` balanceTeams · `0x01191920` joinSquad по токену ·
`0x0118C620` обработчик сообщений персистентности (Create → `0x01188D90(player)` при `+0x318==0 && +0x319==0 && (+0x20|+0x24)!=0`).
