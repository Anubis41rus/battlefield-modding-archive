# Отчёт: поиск функции createPlayer (спавн ботов) — 11.10.2026

## Суть задачи

Lua-боты (мод `fun-bots`) создаются в **реестре** (`PlayerManager:CreatePlayer`
→ `id=30`), но `Player:SpawnSoldierAt` — заглушка. Чтобы боты появились в
матче, нужно научить мод вызывать **движковую** функцию `createPlayer`, которая
создаёт `ServerPlayer` и кладёт указатель в массив менеджера. Адреса этих
функций не были найдены.

## Что установлено о раскладке (Ghidra + живой прогон)

Реверс `ServerPlayerManager::update` (адрес уточнён, см. ниже) дал:

- Массив игроков — **массив указателей**: `[this+0x80] .. [this+0x84]`,
  третий указатель (ёмкость) — `[this+0x88]`.
  Число игроков = `end - begin` (уже в единицах элементов!).
- Второй массив — `[this+0x90] .. [this+0x94]`.
- Для каждого игрока вызывается `ServerPlayer::update`.
- У `ServerPlayer`: `[p+0x10]` = имя, `[p+0x3C4]` = «есть солдат».
- **Прежнее «размер элемента 0x2D0» — ошибка.** Это размер объекта
  ServerPlayer, а в массиве лежат 4-байтные указатели. Из-за этой ошибки
  поиск спавна и зашёл в тупик.

`createPlayer` обязан: выделить `ServerPlayer` → **положить указатель**
в `[this+0x80..0x84]`. Это и есть искомая операция.

## Найдено две ошибки (обе мешали прогрессу)

### 1. Адреса из Ghidra клали как RVA (сдвиг 0x400000)

`InlineHook::Install` делает `moduleBase + rva`, а Ghidra отдаёт **VA**
(ImageBase `0x400000` уже включён). Сложив базу дважды, адрес уезжал на
`+0x400000` в участок заглушек:

| RVA | содержимое | что произошло |
|---|---|---|
| `0x00E5EF00` | `C3 CC CC CC…` | хук «встал» сюда, в трамплин попал `C3` |
| `0x00A5EF00` | `83 EC 08 56 8B F1…` | **настоящий** `update` |

Хук сообщал `Ok`, но **никогда не срабатывал**; трамплин был мусором.
Правило: **адрес из Ghidra вычитать `0x400000` перед переносом в C++**,
и проверять пролог чтением бинаря. Исправлено в `SpmProbe.cpp` и
`EngineHooks.cpp` (там же, вероятно, был дефект у части старых хуков).

### 2. Пробник считал игроков как `(end-begin)>>2`

Массив из одного игрока (4 байта) давал `4>>2 = 0`. Для массива указателей
`end-begin` **уже** число элементов. Исходник движка считает
`((int*)end-(int*)begin)>>2`, т.е. байты/4. Исправлено.

## Почему не нашли createPlayer статикой (тупики)

- `ServerPlayerManager` **не виртуальный**: у `update` ровно одна ссылка —
  прямой `call` из `stepSimulation`. Vtable-подход мёртв.
- **RTTI в бинаре нет** (`/GR-`): нет `.?AV…@@`, Ghidra не создал
  vftable-символов.
- Строки-имена `fb::…::method` **без xref** из кода — только указатели в
  `.data`.
- Кластер функций рядом с `update` — это в основном **триггеры перемещения
  солдата** («Trigger must have a next position…»), не `createPlayer`.

## Решение: guard page (`SpmProbe.cpp`, `LEGACYEXT_SPM_GUARD=1`)

Переносим массив игроков в нашу память так, чтобы **первая же** запись
движка падала на `PAGE_GUARD`:

- выделяем две страницы подряд: `[RW][GUARD]`;
- `begin = end =` начало **guard-страницы**, `capacity =` она же +1 элемент;
- движок видит `end != capacity` и пишет указатель прямо на guard page;
- ловим `STATUS_GUARD_PAGE_VIOLATION` vectored exception handler'ом;
- **адрес виноватой инструкции (EIP) = `createPlayer`.**

Обработчик только запоминает EIP и снимает ловушку; лог пишется из `update`
(писать в файл из обработчика исключения нельзя).

Первая попытка не сработала: массив влез в обычную RW-страницу, guard ждал
1024-го игрока. Исправлено: `begin=end=` на саму guard-страницу.

## РЕЗУЛЬТАТ: полная цепочка создания игрока найдена (13:44)

Guard page сработал: `EIP = 0x00E6C58B` → функция `FUN_00e6c570` (это
`push_back` вектора, а сама createPlayer — её вызывающий). Подъём по цепочке
вызовов дал **весь путь от сетевого сообщения до массива игроков**.

### Цепочка (VA → RVA = VA − 0x400000)

| Уровень | VA | RVA | Что это |
|---|---|---|---|
| 3 | `0xD6EAE0` | `0x96EAE0` | диспетчер сетевых сообщений: `NetworkCreatePlayerMessage` (0xD204CF07) → `FUN_00e48490` |
| 2 | `0xE48490` | `0xA48490` | **обработчик `onCreatePlayerMessage`** (строки «onCreatePlayerMessage: », «Someone is calling req player more than once…») |
| 1 | `0xE6F720` | `0xA6F720` | обёртка: `createPlayer` + `addToArray` |
| 0 | `0xE6CA00` | `0xA6CA00` | **addToArray(player\*, name\*)** — кладёт указатель в `[this+0x80..0x84]` |
| — | `0xE6C570` | `0xA6C570` | `push_back` вектора (**это поймала ловушка**, EIP+0x1B) |

### Ключевые функции для спавна ботов

```c
// FUN_00e6f720 (0xE6F720) — обёртка
int FUN_00e6f720(param_1, param_2, param_3, param_4) {
    iVar1 = FUN_00e644b0(param_1, param_3, param_4);   // ← СОЗДАЁТ ServerPlayer
    if (iVar1 != 0) FUN_00e6ca00(iVar1, *param_2);     // ← кладёт в массив
    return iVar1;
}
```

- **`FUN_00e644b0` (VA `0xE644B0`, RVA `0xA644B0`) — createPlayer.**
  Выделяет и инициализирует `ServerPlayer`, возвращает указатель.
- **`FUN_00e6CA00` (VA `0xE6CA00`) — addToArray.** Кладёт указатель в массив
  и регистрирует игрока в карте имён (`this+0xb0 + i*0x20 + 0x18`).

### Как это вызывается при входе игрока (FUN_00e48490)

```c
uVar6 = FUN_01a433a0();                        // personaref/слот
iVar11 = FUN_00e6f720(uVar6, &name, -1, team); // ← создание игрока
*(int *)(in_ECX + 0x1924) = iVar11;            // «ожидающий» игрок
if (iVar11 == 0) { ... "Failed creating player; disconnecting user" ... }
else {
    *(undefined4 *)(iVar11 + 0x3c0) = *(undefined4 *)(in_ECX + 0x2f10); // солдат
    ...
}
```

Поле `+0x3C0` — ровно то, что мы увидели у живого игрока (`[p+0x3C0] =
0xF2DD3570` — указатель на солдата). Совпадение подтверждает раскладку.

### Бонус: найден спавн солдата

`FUN_00ddbbd0` (VA `0xDDBBD0`, RVA `0x9DBBD0`) — создание игрока **на спавн-точке**,
это то, что нужно для солдата:

- строки: `"Player %s is not allowed to spawn yet."`,
  `"Unable to create player on CharacterSpawnEntity : … will not spawn any soldier"`
- внутри зовёт `FUN_00e644b0(0, param_2, 0)` и `FUN_00e6ca00(...)`
- в конце `FUN_00dd9000(param_1)`

### Точные сигнатуры (из дизассемблирования, не догадки)

`re\spawn_sigs.txt` — дизасмбл трёх функций. Ключевое: соглашение вызова
определяется по `RET 0xN` и по чтению `[ESP+N]` **до** первого `PUSH`:

| Функция | RVA | Сигнатура | Признак |
|---|---|---|---|
| `FUN_00e644B0` createPlayer | `0xA644B0` | `player* __thiscall(mgr, a1, a2, a3)` | `RET 0xC` → 3 аргумента; `MOV ESI,ECX` → this |
| `FUN_00e6F720` обёртка | `0xA6F720` | `player* __thiscall(mgr, a1, a2, a3, a4)` | `RET 0x10` → 4 аргумента |
| `FUN_00E6CA00` addToArray | `0xA6CA00` | `void __thiscall(mgr, player*, name)` | читает `[ESP+0x28]` (после `SUB ESP,0x10` + 4 `PUSH`) |

Разбор обёртки показывает перестановку аргументов при转发 в createPlayer:

```
вход: a1=[ESP+4], a2=[ESP+8], a3=[ESP+0xC], a4=[ESP+0x10]
  PUSH a4; PUSH a3; PUSH a1  →  createPlayer(mgr, a1, a3, a4)
```

То есть **a2 (имя) в createPlayer не передаётся** — имя идёт только в
`addToArray`. Это важно: нельзя тупо скопировать порядок аргументов.

Также из дизассемблирования createPlayer видно, что `this` работает со
**вторым** массивом (`[this+0x90] .. [this+0x94]`, `SAR EDX,2`) и лимитом
`[this+0xA0]`, тогда как `addToArray` кладёт в **первый** (`+0x80`).

### Что сделано дальше: перехват реальных вызовов

Добавлены хуки `SpawnTrace` (`SpmProbe.cpp`), которые логируют фактические
аргументы при живом входе игрока — чтобы **не угадывать** значения:

- `kCreateWrapRva = 0x00A6F720` — пишет `this, a1, a2, a3, a4` и результат

### Подтверждённые сигнатуры всех шести функций (`re\ret_args.txt`)

Число аргументов берём **по immediate в `RET`** — это надёжнее догадок по
декомпиляции. Ошибка здесь ломает стек и роняет сервер.

| Функция | RVA | `RET` | стековых арг. | всего с this |
|---|---|---|---|---|
| `createWrap` | `0xA6F720` | `0x10` | 4 | 5 |
| `createPlayer` | `0xA644B0` | `0xC` | 3 | 4 |
| `addToArray` | `0xA6CA00` | `0x8` | 2 | 3 |
| `onCreatePlayerMessage` | `0xA48490` | `0x4` | 1 | 2 |
| `spawnSoldier` | `0x9DBBD0` | `0x10` | 4 | 5 |
| `soldierSetup` | `0x9D9000` | `0x4` | 1 | 2 |

### ИНЦИДЕНТ: guard page + перехватчики вместе роняют сервер

Первый прогон со всеми шестью хуками **выкинул игрока из игры**. Сигнатуры
оказались верными — виноват не стек, а **одновременная работа guard page**:

1. Guard переносит массив игроков на свою guard-страницу и объявляет
   `end != capacity`, чтобы поймать запись.
2. Перехват записи срабатывает, мы ставим `capacity = конец страницы`.
3. Но `begin`/`end` остались указывать на подменённую память, а у настоящего
   контейнера — своя. Дальше `addToArray` продолжает работу (регистрация в
   карте имён по `this+0xb0`, обращение к `player->vtable`) с испорченным
   состоянием → падение.

**Правило: guard page и наблюдательные хуки не совмещать.** Guard нужен
один раз, чтобы снять адрес; дальше работаем только с перехватчиками.

Что всё же успели узнать из того лога (ценно):

```
TRACE onCreatePlayerMessage(this=F2DD7460 msg=025AE470)
TRACE createWrap(this=F2CC0100 a1=0 a2=1 a3=82243904 a4=-1)
TRACE createPlayer(this=F2CC0100 a1=1 a2=1 a3=4294967295) -> player=F2DDD020
```

- `this` у `createPlayer` = `0xF2CC0100` — **это наш ServerPlayerManager**
  (тот же адрес, что `update` сообщает в пробнике). Подтверждено живьём.
- `createPlayer` **отработал и вернул игрока** `0xF2DDD020` — вызов рабочий.
- `onCreatePlayerMessage` вызывается на другом объекте (`0xF2DD7460`), не на
  менеджере.

### ИНЦИДЕНТ №2: `__fastcall` вместо `__thiscall` — стек едет, сервер падает

Второй вылет. Причина найдена в логе — **аргументы приходили сдвинутыми**:

```
было (лог): createWrap(this=… a1=0 a2=1 a3=114553152 a4=-1)
            createPlayer(this=… a1=1 a2=1 a3=4294967295)
должно быть: createPlayer(mgr, a1=0, a3=114553152, a4=-1)
```

Движок компилирован как `__thiscall`: `this` → ECX, **все** аргументы в стек.
Я объявил detour как `__fastcall`, а тот кладёт **первый аргумент в EDX** —
остальные сдвинулись, и на выходе `RET 0xC` сорвал кадр.

`__thiscall` в MSVC разрешён только на функциях-членах (ошибка C3865), поэтому
рабочий приём — **`__fastcall` с фиктивным параметром**, который забирает EDX
и сдвигает остальные в стек:

```cpp
int __fastcall DetourCreatePlayer(void* self, void* /*edx*/, void* a1,
                                  void* a2, void* a3) { ... }
```

Трюк применяется только к функциям с **2 и более** стековыми аргументами:
при одном аргументе `__fastcall` и `__thiscall` совпадают
(`onCreatePlayerMessage`, `soldierSetup` — оставили как есть).

**Правило на будущее:** перед хуком всегда сверять `RET 0xN` для числа
аргументов **и** соглашение вызова; на x86 `__fastcall` ≠ `__thiscall`
при N≥2.

# Часть 6. МОСТ Lua -> движок: точная схема реализации

## Что выяснено про мод (факт, `BotManager.lua`)

Обе функции **реализованы**, но целиком на Lua и **не связаны с движком**:

## Схема моста (минимум, который нужен)

### 1. Нативная часть (C++, новый модуль, НЕ в SpmProbe)
Две функции, регистрируемые в Lua как ``NativeBridge.*``:
``

NativeBridge.SpawnEnginePlayer(ptr, spawnPointPtr)      -> число (0 = отказ)
``
Первая делает РОВНО то, что уже доказанно работает в пробнике:
1. ``createPlayer(mgr, slot, -1, 0x40603000)`` (RVA ``0x00A644B0``)
2. ``addToArray(mgr, player, name)`` (RVA ``0x00A6CA00``)

  ``ServerPlayerManager::update`` (RVA ``0x00A5EF00``), этот хук стоит
  постоянно в ``EngineHooks.cpp``.
- **слот обязан быть уникальным** — иначе бот вышибает живого игрока
  (наблюдали 14:14). Слот = количество игроков в менеджере + 1.
- Соглашение вызова: движок ``__thiscall`` => в C++ объявлять
  ``__fastcall`` **с фиктивным параметром**, иначе едет стек.

Вторая вызывает ``FUN_00ddbbd0`` (RVA ``0x009DBBD0``) на точке спавна
и под ``__try/__except``.

## ГРАБЛИ (не повторять — каждый стоил прогона или краша)
1. **Соглашение вызова.** Движок `__thiscall` => в C++ объявлять
   `__fastcall` **с фиктивным параметром**, иначе едет стек.
2. **Адреса Ghidra — это VA** (ImageBase `0x400000`), вычитать перед
   сложением с базой модуля.
3. **Число аргументов** в detour сверять с `RET 0xN`, не по памяти.
4. **Слот игрока обязан быть уникальным** — иначе бот вышибает живого.
5. **Lua внутри `R"LUA(...)LUA"`** не использовать escape-последовательности
   C++. `\\"` портит парсинг чанка (`unfinished string`), и вся библиотека
   молча не грузится.
6. **`namespace legacy` внутри файла, уже находящегося в `legacy`**, даёт
   `legacy::legacy::` и `LNK2019`.
7. **Не вызывать движковые функции на незнакомых объектах** — `0xC0000005`.
   Только безопасные чтения.
8. **Переменные окружения в скрипте задаются дважды** — вторая перебивает.
9. **Не убивать `bf3`**, если в нём играет пользователь.
10. **Бэкапить рабочую DLL** в `backup\2026-10-11` перед каждой правкой.
