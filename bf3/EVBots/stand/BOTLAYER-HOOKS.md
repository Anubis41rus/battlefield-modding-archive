# BOTLAYER-HOOKS — механизм хуков и проверенные адреса (фаза 1, шаг 2)

Дата 2026-10-08. Метод: Ghidra 12.1.4 headless + PyGhidra, декомпиляция, затем
**проверка байтов в реальном образе `bf3_server_Final.exe`** через pefile.
Выгрузки декомпиляции: `C:\Games\re\ghidra-hookimpl.txt`, `ghidra-installer.txt`,
`ghidra-patchers.txt`, `addr-classification.txt`, `sig-verification.txt`.

## 1. Главный вывод

Хуки ставятся **не AOB-сканированием**, а **по жёстко зашитым абсолютным
адресам**, с проверкой нескольких байт по этому адресу как **контроль целостности**.
То есть сборка **прибита к конкретной версии** `bf3_server_Final.exe`.

И все хуки нацелены на **серверный** бинарник, а не на клиентский `bf3.exe`.

Это меняет оценку надёжности: переживать обновление игры нельзя, надо либо
перенаходить адреса, либо перейти на AOB самим.

## 2. Установщик хука

Найден через xref на импорт `FlushInstructionCache` + `VirtualProtect` +
`VirtualAlloc` (всего 4 функции; `FUN_10001000` — 7 299 байт, это не установщик).

### 2.1 `FUN_100256f0` / `FUN_10025a00` — основной (573 байт, близнец)

Каждая ставит **ровно один** хук и включается отдельным env-флагом:

| Функция | Флаг | Цель |
|---|---|---|
| `FUN_100256f0` | `BF3ACT_BOTLAYER_NETDMG` | `0x01183000` (ClientDamageListener) |
| `FUN_10025a00` | `BF3ACT_BOTLAYER_CHATPROBE` | `0x00E4DAF0` (ServerChatManager) |

Алгоритм (по декомпиляции):
1. `GetEnvironmentVariableA(<флаг>, buf, 8)` — если не `1`, выход.
2. **Сверка 6 байт** по целевому адресу с эталоном; при несовпадении — лог и выход.
3. `VirtualAlloc(0, 0x20, MEM_COMMIT|MEM_RESERVE, PAGE_EXECUTE_READWRITE)` —
   32 байта на трамплин.
4. Копирует первые **5 байт** оригинала в трамплин.
5. По `+6` пишет `0xE9` (JMP rel32), по `+7` — смещение назад
   (например `0x1182FFB` для NETDMG, `0xE4DAEB` для CHATPROBE).
6. `VirtualProtect(цель, 8, PAGE_EXECUTE_READWRITE)`.
7. **Атомарная запись 8 байт под `LOCK()`**: `E9 BB 25 EA 0E 90 xx xx` —
   JMP в detour + `NOP`-выравнивание. Запись выполняется циклом
   «прочитал → сравнил с ожиданием → записал», пока не сойдётся:
   защита от гонки, если движок патчит тот же код параллельно.
8. `FlushInstructionCache(GetCurrentProcess(), цель, 8)`.
9. `VirtualProtect` — восстановить права.
10. Лог: цель, адрес detour, трамплин, длина, имя флага.

Значит итоговый патч = **8 байт по адресу цели**, оригинальные 5 байт сохранены
в трамплине, `NOP` добивает остаток.

### 2.2 `FUN_10026740` — пробный (468 байт), только TEAMSWITCHPROBE

Универсальный вариант с длиной сигнатуры в параметре:

```c
int FUN_10026740(void* target, const uint8_t* expected, int len,
                 void* detour, void** out_trampoline, const char* label);
```

Алгоритм отличается: сверяет `len` байт (посимвольно), затем **перескан��вает
скопированные байты, чтобы трамплин включал последнее вхождение сигнатуры** —
то есть аккуратно обходит сам патч. Вызывается **всего 2 раза**, оба — из
`FUN_100261d0` за флагом `BF3ACT_BOTLAYER_TEAMSWITCHPROBE`. То есть это
диагностический режим, а не основной путь.

### 2.3 `FUN_10019140` — логгер

`QueryPerformanceCounter` + `GetLocalTime` + `GetCurrentThreadId`, формат
`"%02u:%02u:%02u.%03u [%lu] "`, запись в файл, замер длительности вызова,
счётчики под `LOCK()`. Включается глобальным флагом.

## 3. Проверенные адреса и сигнатуры

Извлечены из `.rdata` DLL и **сверены с байтами в реальном образе**.

| Хук | Адрес (VA) | RVA | Байты-сигнатура | Проверка |
|---|---|---|---|---|
| NETDMG (ClientDamageListener) | `0x01183000` | `0x0D83000` | `55 8B EC 83 E4 F0` | ✅ MATCH |
| CHATPROBE (ServerChatManager) | `0x00E4DAF0` | `0x0A4DAF0` | `81 EC B4 02 00 00` | ✅ MATCH |
| ServerPlayerSquadManager::onNewRound | `0x0117EA40` | `0x0D7EA40` | `8B 44 24 04 8B 0D D8 D7 B5 02` | ✅ MATCH (единственное вхождение в файле) |
| ServerPlayerSquadManager::switchTeams | `0x0117EBE0` | `0x0D7EBE0` | `A1 D8 D7 B5 02` | ✅ MATCH |

Значения скобятся так: `push ebp; mov ebp,esp; and esp,-16` · `sub esp,0x2B4`
· `mov eax,[esp+4]; mov ecx,[0x02B5D7D8]` · `mov eax,[0x02B5D7D8]`.

### 3.1 Какой это бинарник

| Образ | ImageBase | SizeOfImage | Файл |
|---|---|---|---|
| `bf3.exe` (клиент) | `0x00400000` | 32.5 МБ | 33 239 896 б |
| `bf3_server_Final.exe` (сервер) | `0x00400000` | 41.0 МБ | 39 416 320 б |

**Все сигнатуры встречаются в серверном образе и ни разу — в клиентском**
(проверено поиском по всему файлу: 41/21/1/10 вхождений в сервере, 0/0/0/0 в клиенте).

⚠️ Замечание о методе: первая попытка определить владельца адреса «по диапазону»
была **неверной** — у обоих образов одинаковый `ImageBase`, а сервер больше
клиента, поэтому диапазоны перекрываются и любой адрес подходит обоим.
Правильный способ — искать сами байты сигнатуры.

## 4. Прочие адреса из декомпиляции

- `0x01182FFB`, `0x00E4DAEB` — точки возврата трамплинов (цель + 11).
- `0x0113DD3C`, `0x012F5285`, `0x0132FFB4` — сверка в `FUN_100262e0`, которая
  выбирает имя хука по адресу (ветвление по трём значениям).
- `0x00E78080` — `ServerProjectileEntityUpdater::update` (из строки-аннотации).
- `FUN_100262e0` обходит очередь из **11 записей** (шаг `0x58`, предел `0x2C0`),
  не более 64 за раз, под `LOCK()` — пакетная установка хуков.

## 5. Что это значит для LegacyEXT (фаза 4)

1. **Инъекция и обход совпадают**: LegacyEXT внедряется тем же `activation-loader
   --dll`, хуки ставим так же. Отладка нашего кода пойдёт по той же схеме.
2. **Хрупкость адресов — наш выбор.** Раз сигнатуры короткие (5–10 байт), сделать
   устойчивые AOB реально: у `onNewRound` 10-байтовая сигнатура **уникальна** во
   всём файле — эталон устойчивого якоря. Остальные нужно расширить
   контекстом справа/слева.
3. **Точки входа для Lua уже есть**: 9 подтверждённых функций движка,
   минимум 4 с проверенными адресами. Остальные — из аннотаций автора.
4. **Порядок работы**: сначала `onNewRound`/`switchTeams` (длинные уникальные
   сигнатуры) как проверка концепции, потом остальные по мере надобности.
5. Все хуки — на **серверном** бинарнике, поэтому серверные боты (своя цель
   LegacyEXT) — правильный первый случай.
