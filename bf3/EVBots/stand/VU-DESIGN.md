# VU-DESIGN — можем ли мы сделать локальный аналог VU, и без server key

Дата 2026-10-08. Ответ по документации VU-Docs + по разобранному бинарнику
`veniceext.dll` + по тому, что уже работает в `BF3LegacyLan`.

**Короткий ответ: да.** Аналог собирается целиком локально, интернет и
**server key не нужны вообще**. Ниже — почему, по пунктам.

## 1. Что такое server key в VU и зачем он

Из `VU-Docs\content\hosting\prereq.md`:

> For each server you wish to run, you will need to generate a unique server key.
> To generate a key … login to the VU website … visit the key management portal
> (`veniceunleashed.net/keys`). Download your server key … place it in the `Server`
> folder and name it `server.key`.

Из `general\commands.md` и `general\args.md`: GUID ключа = ID сервера,
по нему работают `connect <GUID>` и схема `vu://join/<server-id>`.

Назначение ключа — **идентификация сервера для онлайн-бэкенда Zeus**: чтобы
сервер появился в общем списке и чтобы Zeus принял его как «свой».
Это **не** механизм защиты клиента BF3 и не криптография игрового протокола.

## 2. Почему ключ можно выкинуть целиком

Ключ проверяет **только Zeus**. Схема VU:

```
клиент BF3 ──► VU-клиент ──► интернет ──► ZЕUS (аккаунты, список серверов,
                                        server keys, NAT-детект, обновления)
```

Убираем Zeus — и у ключа не остаётся авторитетной стороны:

| Что делал Zeus | Чем заменяем в Legacy |
|---|---|
| аккаунты/солдаты | уже есть: `BF3LegacyLan\profiles\`, персоны |
| список серверов (браузер) | свой `GET /servers` в нашем backend (уже есть `HttpListener`) |
| server keys | **своя схема идентификатора сервера** — любой GUID, который назначим сами |
| раздача обновлений | не нужна (всё локально) |
| NAT/IP-детект | свой LAN-автодетект (в VU это `GetAdaptersInfo` — мы видели в `vu-core.dll`) |
| вход по прямой ссылке | уже работает: join по `TARGET=IP:25300` |
| `-unlisted` | уже есть фактически |

**Вывод: server.key — сервисная функция, а не протокольная. Локально она
нерелевантна.** Вместо неё — свой идентификатор сервера, и всё.

## 3. Что на самом деле нужно, чтобы клиент BF3 зашёл на сервер

Не Zeus и не ключ, а **протокол Blaze/Harmony** между клиентом BF3 и сервером
плюс игровые данные. И это у нас **уже работает**:

| Что | Где | Статус |
|---|---|---|
| Редиректор 42127 + Blaze 10041 | `BF3LegacyLan\backend\BF3LegacyLan.Backend.exe` | ✅ работает |
| Игра создаётся, GID выдаётся | там же, `GameManagerService` | ✅ работает |
| Join-пакет обрабатывается | `joinGame`, `ClaimingReservation`, `UserAdded` | ✅ работает |
| Редирект клиента на игровой порт 25300 | `join.bat`, `activation-loader` | ✅ работает |
| Референсы протокола для углубления | `Legacy\New-Blaze-Emulator\`, `Legacy\openBlase\` | ✅ есть исходники |

По `RECON.md` наш backend уже реализует flow зевусского вида:
`fetchClientConfig` → `GAME GID` → `joinGame` → `ClaimingReservation` →
`UserAdded` → `JoiningPlayerInitiateConnections`. Т.е. **серверная часть
протокола у нас закрыта**, не хватает только браузера серверов.

## 4. Архитектура Legacy (собираемое)

```
                    интернета НЕТ
┌───────────────────────────────────────────────────────────────┐
│  bf3.exe / bf3_server_Final.exe  (x86, НЕ модифицируем)        │
│      ▲                                                         │
│      │ вызовы движка (хуки)                                    │
│  legacyext.dll          ← ВЕСЬ наш код. 1 экспорт:            │
│      ├── GetModdingInterface() → объект с vtable (~5 методов)   │
│      ├── Lua 5.4.2 (lua.dll) + SOL3 → биндинги типов           │
│      ├── таблица нативов движка (init, как vtable[0] у VU)     │
│      └── хуки движка по адресам из HOOK-TABLE.md (8 шт.)        │
│           ▲ внедряется тем же: activation-loader --dll        │
└───────────┼───────────────────────────────────────────────────┘
            │
┌───────────┴──────────────┐        ┌──────────────────────────────┐
│ Наш лаунчер (vu.exe-аналог) │───────►│ Наш backend (Zeus-аналог)    │
│ список серверов, вход 1 клик│        │ Blaze+редиректор (готов)    │
└──────────────────────────┘        │ + GET /servers (фаза 2)     │
                                       └──────────────────────────────┘
                                                    │
                                          LAN, адрес известен
                                                    ▼
                                            bf3 (клиент гостя)
```

**Ни VU, ни его файлы не модифицируются.** Мы пишем свою DLL и свой бэкенд.
`veniceext.dll` используется только как **образец архитектуры** (у нас уже
извлечён контракт: 1 экспорт + 5 методов vtable).

## 5. Что берём у VU по образцу (уже извлечено)

| Образец | Наш аналог |
|---|---|
| 1 экспорт `GetModdingInterface`, объект с vtable из 5 методов | то же в `legacyext.dll` |
| `lua.dll` **Lua 5.4.2** | та же версия — совпадёт семантика API ботов |
| **SOL3** для биндингов (7069 RTTI-строк) | SOL3 (MIT) вместо 303 ручных обёрток |
| загрузка модов `luaL_requiref` | тот же механизм, структура `Admin/Mods/<имя>/mod.json` |
| планировщик на fibers | наш выбор; тик от хука `TICK` (`0x00E5EF00`) |
| таблица нативов движка, заполняемая при init | своя таблица |
| API-поверхность: 303 элемента (303 подтверждено: 98 типов + 15 менеджеров) | реализуем нужное подмножество |

## 6. Новый результат: как VU цепится к движку

Проверено точным методом (prefilter по опкодам `push/mov/cmp/C7 imm32`
+ подтверждение Capstone; наивный скан по любым 4 байтам дал 247 297 мусоров,
этот — **221 уникальный адрес, 357 ссылок**):

- VU **записывает абсолютные адреса движка в таблицу** при инициализации:
  `mov dword ptr [0x18E74D30], 0x45B570` и десятки подобных в диапазоне
  `0x18E74Cxx..0x18E753xx`. Это и есть работа метода `[0]` vtable —
  он заполняет ~30 таблиц нативов Frostbite.
- Распределение: **212 адресов в `bf3.exe`** (клиент) и **9 в
  `bf3_server_Final.exe`** (сервер). То есть VU работает в основном на клиенте.
- **Ни один из наших 8 адресов botlayer в этом списке не встречается.**
  Это ожидаемо: бот-слой хукает одни функции движка (логика бота), VU — другие
  (моддинг, UI, данные). **Пересекаться им незачем.**

Вывод для нас: адреса VU нам не нужны как таковые — нужен **механизм**
(таблица нативов, инициализация, SOL3-биндинги) и наши собственные хуки.

## 7. Ответы на вопросы

**«Можно вообще без server key?»** — да. Он проверяется только Zeus'ом;
без Zeus'а нет и проверки. Заменяется собственным GUID.

**«Можно ли собрать аналог VU, работающий чисто локально?»** — да. Протокол
Blaze у нас уже работает, бэкенд уже есть, осталось добавить браузер серверов
(фаза 2) и написать свою DLL (фаза 4). Интернет не требуется нигде.

**«Мы модифицируем VU или BF3?»** — нет. Мы пишем **своё**: `legacyext.dll`
и свой бэкенд. BF3 не трогаем (только хуки в памяти процесса, как это делает
любой мод). VU используем как образец и как источник документации.

**«Насколько это реально?»** — по объёму: контракт из 5 методов уже понятен,
SOL3 снимает вопрос с обёртками, 8 хуков с адресами и сигнатурами получены.
Основная неизвестная — как `veniceext` резолвит нативы под разные версии BF3
(нужен разбор таблицы `0x18E74xxx`).

## 8. Что я сделал с проблемой RAM (как просили)

Ghidra на 149 МБ не влезает в 8 ГБ. **Обошёл без него:**

1. **Точечный дизассембл Capstone** — экспорт `GetModdingInterface` и 5
   методов vtable целиком разобраны за секунды, ~30 МБ памяти.
2. **Потоковое сканирование строк блоками по 4 МБ** — 151 048 строк, память
   не зависит от размера файла.
3. **Prefilter по опкодам + Capstone** — 221 адрес движка, ~300 МБ памяти.

Расход памяти вместо 5–7 ГБ — около 300 МБ. Ghidra понадобится только для
сопоставления с botlayer; это можно сделать на машине с 16+ ГБ либо
поэтапно (импорт с отключёнными анализаторами и таймаутом на файл).
